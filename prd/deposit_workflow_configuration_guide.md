# 充值咨询与异常处理：工作流配置样例

版本：2026-10-15。交付范围：八条计划工作流中的第一条，用于确认配置说明的粒度。

2026-10-16 网站配置更新：已在指定 UAT 网站补齐、优化并发布同名工作流。网站与本地演示版的节点字段不同，当前发布版本为 28 个节点、32 条连线；网站配置以第 10 节的适配记录为准，以下原始样例保留作为设计依据。

本手册按当前 AI Agent 工作台实际字段编写，提供名称、触发提示词、25 个节点的填写内容、连线和验收场景。它是手工配置指南，不是可导入文件；当前产品没有本手册对应的一键导入入口。

语言约定：节点名称、提示词、询问内容和客户回复统一使用中文；变量名、接口字段、提取路径及状态值保留英文，确保引用与判断一致。下文的中文话术可直接填入产品；不要把 `{{变量名}}` 中的英文翻译成中文。

转换时保留以下区别：

- 充值延迟不等于维护。只有维护状态经渠道或 BO 证实，才进入维护回复。
- BO 显示完成不自动等于已核实钱包入账；「余额已使用」必须有对应账本记录。
- 未查到记录、凭证缺失、凭证不属于本渠道、金额或时间不一致不能互相替代。
- 原文没有 API 地址、错误码、品牌到账 SLA 和恢复时间；本手册不补造这些事实。
- 「结束」只结束本次工作流，不代表关会话、解决工单或停止人工跟进。
- 原文 GCash 步骤不能推广到所有渠道。N04 明确其适用范围，并避免保证即时到账。

在「资源中心 → 工作流 → 创建工作流」填写：

| 字段 | 填写值 |
| --- | --- |
| 工作流名称 | 充值咨询与异常处理 |
| 触发提示词 | 当用户询问如何充值、反馈充值未到账或余额未显示、充值延迟、无法充值或充值页面报错时使用。先区分操作咨询与已发生的交易异常。仅游戏扣款争议、提现、账号找回、优惠奖励问题不使用本流程。用户同时提出多项问题时，先澄清本次充值诉求。不得仅凭用户描述认定已到账、已消费、维护中或已经转交人工。 |

### 3.1．流程结构

```text
N00 开始
  -> N01 收集诉求 -> N02 AI识别 -> N03 诉求分流
       + 教程 -> N04 操作指引 -------------------------------> N24 结束
       + 交易异常 / 充值报错 -> N05 收集资料 -> N06 查询 -> N07 核验分流
       |   + 已入账 -> N08 ---------------------------------> N24
       |   + 已使用 -> N09 ---------------------------------> N24
       |   + 处理中 -> N10 -> N16 提交核查 -> N17 提交结果
       |   + 失败 -> N11 ---------------------> N24   + 已受理 -> N18 -> N19 等待
       |   + 维护 -> N12 ---------------------> N24   |   + 业务结果 -> N20 -> N24
       |   + 缺资料 -> N13 -------------------> N24   |   + 超时 -> N21 -> N24
       |   + 非本渠道凭证 -> N14 -------------> N24   + 其他情况 -> N22 -> N24
       |   + 其他情况 -> N15 -> N16
       + 其他情况 -> N23 澄清 -------------------------------> N24
```

所有编号仅用于本指南定位，不是产品生成的内部节点 ID。除开始节点外，将「节点名称」填写为下文章节名，例如「N06 核验充值记录」。开始节点使用系统默认名称，结束节点使用创建时已有的结束节点即可。

### 3.2．统一填写约定

- 「固定回复」节点的「回复内容」可以直接复制；附件和知识库在本样例均留空。
- 收集信息、AI任务、调用接口可以产出变量；先连线并配置上游输出，再在下游选择变量。
- 本样例的输出名全流程唯一。文本中的 `{{username}}` 等短引用符合当前校验规则。产品「插入信息」或「入参引用」生成的 `{{实际节点ID:变量名}}` 也可使用，优先通过选择器插入。
- 条件表的「判断信息」必须在下拉框中选择指定上游结果，不把变量名当作用户输入或手工常量。
- 「任务结果」和值／提取路径的实际解析由未来执行引擎决定。N02 的 JSONPath 是建议契约，不表示当前演示已经能运行结构化模型输出。
- 不在任何文本框中填写 `{{N06:lookup_result}}`；N06 是文档编号，产品内部 ID 由系统生成。

`brand` 是为多品牌查账增加的定位字段；币种和时间中的时区用于避免交易误匹配，属于配置建议而非原文新增业务政策。用户名、订单号必须用文本，保留前导零。金额未知留空，不能默认填 0；数字节点本身没有金额大于 0 的校验项，须由接口校验。

`receipt_reference` 只表示已上传凭证或报错截图的安全引用，不是图片二进制，也不是让客户填写任意下载网址。原文要求交易核验时提供凭证；这里设为可选是为了兼容「尚未支付」「订单号未知」场景，不意味着核验可以跳过凭证要求。N06 必须针对实际场景检查资料是否充分。

当前收集节点没有文件类型，渠道上传消息也没有自动映射到此变量的已实现能力。演示时可填写 `demo-receipt-001`；真实接入由附件服务生成引用。没有映射时，仅能由人工查看凭证，不能声称已自动识别或对比。出口接 N06。

以下是待对接契约，BO 现有状态码需要映射，不直接使用未经核实的原始字符串：

| lookup_result | 必须具备的证据／含义 |
| --- | --- |
| credited | 唯一匹配到订单，并核实该笔充值已进入正确账户钱包；返回 checked_order_id |
| used | 已核实入账，且账本能证明该笔对应余额随后已被使用；不能仅因当前余额为零就返回此值 |
| pending | 唯一匹配到对应交易，其状态为 Pending／Processing，满足提交 Admin 核查所需资料 |
| failed | 核实 Failed／Rejected，或核实未支付／受限等失败原因；customer_message 必须包含可对客披露的原因与下一步 |
| maintenance | 已核实影响本次充值的维护公告或支付渠道状态；不得由用户猜测推导 |
| need_info | 资料不足，无法唯一匹配交易或完成必要凭证核验；customer_message 必须具体列明缺什么 |
| not_ours | 凭证经核实不属于本平台支付渠道；只有缺图或未识别不能返回此值 |
| unknown | 无法确认、信息矛盾、凭证金额／时间与 BO 不一致，或查询服务不可用；不得自动判失败、到账或维护 |

接口处理顺序：先确认身份／品牌匹配，再核验资料和交易唯一性、凭证归属及金额时间一致性，最后判定业务状态。钱包已入账／已使用可按原文用户名查账场景在证据充分时返回；无法完成该核查时不能省略凭证。

未支付且尚无订单时，应依据错误截图和维护信息排查，不强制要求不存在的订单号。多笔候选交易不得默认选最新一笔。

`customer_message` 必须是审核后可对客展示的中文文本；不得直接透传内部错误栈、第三方原始报错或账户敏感数据。`evidence_summary` 供后台核查团队使用，采用中文说明已核验结果与缺失项，不拼接密钥。接口字段名及状态值仍保留英文。字符串缺失统一为空字符串；可选金额缺失使用空值而不是 0。异常响应、HTTP 失败、空白必需消息均需由适配层归一为 `unknown`；当前节点没有错误出口，未实现此适配前异常路径无法闭环。出口接 N07。

## 6．实际配置顺序

1. 创建工作流，填写第 3 节名称和触发提示词。
2. 保留已有开始／结束节点，添加其余 23 个节点，按章节编号命名。可以按「意图识别、交易核验、后台核查跟进」从左到右摆放。
3. 先填写 N01、N02、N05、N06、N16 的信息项和输出名；输出值按表格填写，不把 `$.xxx` 当作已返回的业务结果。
4. 在 N03、N07、N17 创建对应分支，先填名称并建立第 5 节连线，再选判断信息。否则上游变量可能不会出现在下拉框。
5. 配置条件值、全部回复和 N19；通过下拉框插入信息时确认来源正确。N16 只能引用在 N10 和 N15 两条路径上都已执行的上游节点；本样例引用均来自它们共同经过的 N01、N02、N05、N06。
6. 演示时两个接口地址保留 `.invalid` 占位，知识库、附件、请求头、请求 Body 留空。真实接入时须替换已确认契约；若后端要求 JSON Body，字段类型和缺省值由适配层正确序列化，不把数字和空值一律转成字符串。
7. 等待顶部显示「已保存」，刷新核对配置是否保留。保存失败先重试，不继续发布。
8. 在隔离演示数据中执行发布校验，修复缺字段、无效引用、断线等提示。该步骤只验证配置完整性，不验证接口能用或业务结果正确。
9. 工作流成功发布后，在目标 AI Agent 的「工作流 → 绑定工作流」中选择它；绑定写入 Agent 草稿，按产品规则发布 Agent 后才生效。本手册没有替你执行任何发布或绑定。
10. 已发布后修改工作流草稿不会改变当前使用版本，再次发布才更新；避免在已有线上依赖的流程上用演示占位覆盖正式配置。

| 只问充值教程 | deposit_intent=tutorial | N03 → N04 → N24，不收集账户或调用 BO |
| 已付款未到账 | deposit_intent=transaction | N03 → N05 → N06，不回复教程 |
| 无法打开充值页 | deposit_intent=access_error | N03 → N05 → N06，不强制索要不存在的订单 |

| 已入账 | lookup_result=credited，已核实订单 | N07 → N08 → N24，不自动创建核查单 |

| 凭证金额／时间不符 | lookup_result=unknown | N07 → N15 → N16，保留矛盾供人工核查 |
| 非预期 BO 状态 | lookup_result=unexpected | N07 默认出口到 N15，不告知成功或失败 |
| 查询接口超时／报错 | 适配层返回 unknown | N15 → N16；没有错误归一适配时应报告执行失败，不称流程已闭环 |
| 核查请求提交失败 | submission_status=failed | N17 → N22 → N24，不发送已转交话术 |
| accepted 但无编号 | 适配层改为 failed | 同提交失败；表单校验本身不会替代接口契约检查 |
| 已有最终核查反馈 | review_state=resolved，有 review_message | N19 业务结果 → N20 → N24，反馈内容与当前核查单一致 |

| 数字和字符串边界 | 用户名 00123、订单 000456、金额缺失／0／负数 | 保留前导零；缺失不替换成 0；不合法金额由接口校验而非伪造表单规则 |
| 真实运行缺附件映射 | receipt_reference 无法产生 | 不声称已读图；由人工查看或提示依赖未完成 |
| 补资料后重入 | 同一用户、同一笔交易 | 复用已知资料与有效核查单，避免重复收集和重复提交 |

客服规则的应用边界：

- 正常对话 1 分钟内回复属于运行调度／服务 SLA，不通过增加等待节点实现。
- 等待期间最多 4 分钟更新，N19～N21 只表达一次更新；不得无条件循环催办。
- 解决后的 1～3 分钟跟进、客户明确无需协助后关会话，依赖会话状态和产品接待设置。本样例不通过结束节点冒充关会话。
- 凭证、余额、状态未知时明确尚未确认；Admin 未受理前不称已转交。
- 已提供的信息尽量复用，固定回复不追问无关字段。本样例已将原文话术按业务含义整理为中文；接口返回的 customer_message、review_message 也须为审核后的中文，不能只翻译固定文案而漏掉动态回复。目标渠道需要其他语言时，应统一审核后替换，不依赖固定回复节点自动翻译。

### 10.1 充值报错回复优化（2026-10-16）

入口由两个 AI 任务收敛为一个内部提取与分类节点，固定只生成 `request_text` 与 `deposit_intent`。已付款未到账进入 N05A，未付款报错进入 N05B；两类资料收集均使用固定中文首问，规避动态变量作为首问时出现的重复输出。未付款报错补齐资料后进入独立的 N27B 人工协助，不调用依赖订单数据的已付款查询接口。
